# v0.2 最小运行时检测设计

状态：设计提案，运行时后端尚未实现。本文不表示当前版本已经能够隔离或运行 C 程序。
只读环境清单及第一阶段结论见 [环境核查与隔离方案](runtime-v0.2-environment.md)。
核对日期：2026-11-10。首先面向开发者的 WSL Ubuntu 24.04 / Clang 18 环境。

## 1. 本阶段要解决的问题

现有 diagnose.py 只做语法和语义检查。v0.2 首先验证一条完整流程：
将单个教学 C 文件复制到受控工作区，在隔离环境编译并运行，定位实际执行路径上的整数除零，保留原始报告并提供中文解释。

完成标准是隔离、资源限制、错误分类与检测结果均可复现；不以“能够启动可执行文件”作为完成标准。

## 2. 最小范围与兼容性

- 单文件 C17、小型本地教学程序，主源码仍限制为 64 KiB。
- 不接受命令行参数、交互输入或用户自定义编译参数；程序 stdin 连接到空输入。
- 仅向编译器提供源码副本和必要的只读工具链、标准头文件与运行库；不提供原始项目目录或自定义头文件。
- 首个解释目标为已经验证形式的整数除零报告；不承诺检测全部未定义行为、内存错误或逻辑错误。
- 不提供 Web 接口、多人任务调度、执行可视化和自动修复。
- 使用独立的运行时检查入口，具体文件名在实现时确定。现有 diagnose.py 的命令、字段、警告策略和退出码保持兼容。
- 初期只有隔离与资源策略验证通过的环境可以启用；其他环境返回明确的工具错误。

“通过”只表示本次路径上未检测到所支持的问题，不证明程序正确。程序返回非零也不能单独证明存在 C 语言错误。

## 3. 检测技术候选

优先评估 UBSan 的单项检查，而不是同时启用多个检测家族：

```text
-x c -std=c17 -O0 -g -fno-omit-frame-pointer
-fsanitize=integer-divide-by-zero
-fno-sanitize-recover=integer-divide-by-zero
```

这些是候选编译参数，不是可绕过隔离直接执行的操作步骤。原型需验证该环境能编译、链接、定位源码并在首个检测失败后停止。
Clang 官方文档说明了该检查选项和停止恢复选项；工具存在或运行库文件存在，都不足以证明完整流程可用。

分类必须同时考虑检测报告、进程返回值和资源管理器结果。只把已经验证的报告形式转成中文诊断，未知信息保留原文。
不能将任意标准错误中的相似字符串宣称为不可伪造的检测证据。

## 4. 必须先完成的隔离条件

隔离同时覆盖编译和运行，不能在沙箱外先调用编译器处理待检查源码。

1. 使用非特权执行边界，限制提权；不能向受检程序传递宿主的管理能力。
2. 为每次任务创建私有工作区，固定沙箱内源码路径，例如 /work/source.c；不直接使用用户输入作为挂载参数。
3. 工具链与必要系统库只读。宿主用户目录、Windows 挂载目录、仓库的 .git、SSH 密钥、令牌和服务套接字不可访问。
4. 受检进程无网络访问能力，且不能通过继承的网络描述符、代理变量或宿主服务套接字间接联网。
5. 清理环境变量，只保留固定运行所需的最小集合；不传递凭据、编译器注入变量或动态库注入变量。
6. 写入仅限有配额的私有工作区，不允许向宿主项目或其他路径写入。
7. 能可靠终止并回收整个任务的子进程，包含父进程退出后仍存活的后代。
8. 启动前确认全部资源限制已经生效；缺失、失败或无法验证时拒绝编译和运行，不能降级为直接执行。

候选方向是 bubblewrap 配合可用的资源控制机制。bubblewrap 的保护效果取决于具体策略，本身不等于现成的完整沙箱。
仅有 unshare、timeout 或进程组终止，也不足以满足上述全部条件。具体挂载、系统调用限制和资源控制方案需单独验证后才能确定。

## 5. 资源预算草案

以下数值是原型验收起点，尚未实测，不应在发布文档中标为已生效的保证。

| 项目 | 编译阶段 | 运行阶段 |
|---|---|---|
| 墙钟时间 | 5 秒 | 2 秒 |
| 内存预算 | 512 MiB | 128 MiB |
| 进程/线程数量 | 整个任务最多 16 个 | 整个任务最多 16 个 |
| stdout + stderr | 每阶段合计 1 MiB | 每阶段合计 1 MiB |
| 可写空间 | 整个任务合计最多 8 MiB，另设文件数量上限 | 共享该任务的剩余配额 |

- 输出边收集边检查，超限立即结束任务；不能先无限收集再截断。
- 时间限制之后还必须完成终止和回收；超时阈值不是整个调用返回时间的绝对上限。
- 仅限制单个文件大小不能保证总磁盘预算；仅限制单个进程也不能保证整个任务的内存和进程预算。
- 可评估 cgroup v2 的内存和进程控制，但必须验证委派权限、实际约束及任务清理。控制器名称可见不代表当前用户能够使用。
- 资源上限与工具链开销需要共同验证；不能为了让正常样例通过而取消限制。
- 本工具不自动安装系统软件、修改系统配置或调整宿主网络及代理。

## 6. 新入口的结果约定草案

本节是待原型验证的契约，不是现有 diagnose.py 的输出变更。

| status | 含义 | CLI 退出码 |
|---|---|---|
| passed | 编译成功、程序返回 0，未检测到支持的问题 | 0 |
| compile_failed | 隔离内完成编译检查，但源码未通过 | 1 |
| runtime_error | 检测到支持的整数除零报告 | 1 |
| program_failed | 无已识别的检测报告，但程序非零退出或异常终止 | 1 |
| tool_error | 隔离、工具、资源控制或清理过程失败 | 2 |

建议字段：

- schema_version：新入口独立的报告版本，首版为 1。
- file：用户请求检查的文件，与沙箱内临时路径分开。
- stage：isolation、compile 或 run，指出结果对应的阶段。
- status / success：按上表表达结果；success 仅在 passed 时为 true。
- diagnostics：结构化诊断，包含类型、位置、原始信息和有限中文解释；未知位置可为空。
- compiler_output：编译器原始标准错误；不与程序输出混在一起。
- stdout / stderr：受检程序两路原始输出，经过有界收集和容错解码。
- program_exit_code：尚未运行时为 null；运行后保留返回码，POSIX 信号终止保留负返回码。
- error：工具错误的 code 和 message；正常的源码检查失败及检测到整数除零时为 null。

工具错误至少区分 SANDBOX_UNAVAILABLE、SANDBOX_FAILED、LIMITS_UNAVAILABLE、SANITIZER_UNAVAILABLE、COMPILER_TIMEOUT、RUNTIME_TIMEOUT、OUTPUT_LIMIT_EXCEEDED、RESOURCE_LIMIT_EXCEEDED 和 CLEANUP_FAILED。
编译器崩溃应归类为工具错误，不能直接解释成源码错误。阶段和未执行字段需有契约测试。

沙箱内报告通过固定源码路径映射回输入文件。无法可靠映射的位置保留原文，不猜测或伪造位置。
初版不依赖英文报告里的绝对宿主路径，也不能直接把 UTF-8 字节列号当作界面字符下标。

## 7. 验收用例与实施顺序

先逐项验证隔离和资源约束，再运行检测样例。所有探针均使用项目内临时测试数据，并先采用很小的资源预算。

| 用例 | 要验证的结果 |
|---|---|
| 隔离工具不存在或启动失败 | 在编译前返回工具错误，没有受检程序被启动 |
| 尝试读取工作区外的专用测试标记文件 | 无法取得标记内容；不使用真实私密文件做探针 |
| 尝试写入任务工作区之外 | 失败，宿主标记文件和目录内容保持不变 |
| 隔离网络验证 | 在测试环境确认受检进程没有外部通信路径；不修改宿主网络配置 |
| 正常单文件程序 | passed、返回 0，输出可复现 |
| 整数除零及对应正确程序 | 能区分两者，错误行与原始 UBSan 报告可追溯 |
| 语法错误 | compile_failed，运行阶段未启动 |
| 显式 return 3 | program_failed，不能擅自解释为某种未定义行为 |
| 死循环、持续输出、受控内存/进程/磁盘探针 | 各项预算分别生效，整个任务均被清理 |
| 未识别报告及工具链版本变化 | 原文保留，不生成未经验证的中文解释 |
| 现有命令回归 | 原有全部测试仍通过，现有 JSON 与退出码语义不回归 |

建议依次交付四个可审查的小阶段：
1. 环境能力说明及隔离方案选择。
2. 隔离启动、资源预算和清理原型及其验收。
3. 整数除零与正确程序的检测原型。
4. 报告契约、错误处理、回归、文档与发布候选。

此阶段不承诺发布日期。隔离验收未完成时，检测功能不进入“可用”状态。

## 8. 现有开发环境只读核查

2026-11-10 的核查结果：

- Ubuntu 中的当前执行用户非 root。
- Clang、unshare、prlimit、timeout 可找到。
- Clang 的资源目录存在 x86_64 UBSan standalone 静态库与动态库；未在本轮编译或运行 UBSan 程序。
- bwrap、Docker 和 Podman 未在当前 PATH 中找到。
- cgroup v2 可见 memory、pids 等控制器名称；未验证可用的委派权限或任何限额。
- max_user_namespaces 为正；unprivileged_userns_clone 对应文件不存在。两者均不能证明实际的用户命名空间创建能力。
- 未安装软件、启动容器服务、调整内核开关或修改网络与代理。

当前结论：还不具备经过验证的隔离执行环境。下一步先决定如何提供隔离组件，再做受控验收。
在保持宿主文件不变的约束下，应先评估项目内提供组件的可行性与维护成本；任何系统级安装或配置均需另行明确范围。
